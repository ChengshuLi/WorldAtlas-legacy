# Data and application architecture

WorldAtlas separates stable territorial identity, geographic reference, dated facts, source evidence and presentation. Application code and factual content are independent. `data/world-index.json` and `data/hierarchy.json` define reference entities; geography is not rewritten by attribute imports. Locations are indivisible polygons with stable IDs; parent membership, names, existence, ownership, environmental classes and other facts have separate records and dates. `src/attributes.js` and `src/temporal.js` implement field-specific resolvers. `hosted/` contains service modules, `drizzle/` contains versioned migrations, and current machine schemas/configuration are the executable contract.

## Storage and compatibility

Stable entity IDs do not encode a display name or owner. Names, memberships, existence, categories, classifications and factual records have distinct identities and intervals. Records use half-open supported dates. Resolvers apply field-specific evidence priorities and then a stable record-ID tie-break; this selects deterministically rather than rejecting every equal-priority disagreement. Explicit unresolved statuses remain unresolved, and particular settlement/habitation conflicts become disputed under their field-specific rules. See `src/evidence-priority.js`, `src/attributes.js` and `src/temporal.js` for the implemented policy. Source identities, factual claims, retirements, geographic releases and typed evidence are immutable/append-only under schema guards; correction uses a new record and the supported retirement/migration path. Do not mutate or repurpose an applied migration, archived record or category identity. Unknown values are explicit and do not trigger silent substitution. Keep local fixtures, hosted databases, raw source files and object/media storage distinct; a local SQLite database is not synchronized with a hosted service.

Category identity and display are separate: `src/category-presentation.js` keys political/cultural/religious presentation using stable category IDs plus the shown name, while `src/category-palette.js` is a generated presentation artifact, not a source of identity or ownership. Its constraints and generator are tested in `test/category-palette.test.mjs` and `scripts/install-category-palette.mjs`.

Typed observation modules are registered through the shared module registry and expose a versioned read/validation contract. Observation rows link a subject and source to a field, value, method, status and supported interval; feature links are separately typed. Adding a module does not authorize research imports or alter geography. Forward schema/storage changes require a new reviewed migration and old/new consumer compatibility tests; preserve original export formats and migration history. Footprint and dated geographic products are versioned separately from factual records. Rebuild only products whose declared inputs changed, and preserve exact source/selector pins.

## Package and API boundaries

Package input declarations and verification policy are defined by `.github/package-inputs.json`; scripts consume declared inputs, not a worker's untracked local database or undeclared files. Hosted API schemas, module interfaces, migration definitions and package controls are maintained in code. Read those sources directly for exhaustive fields and current endpoints instead of copying generated inventories here. A documented repository capability is not proof of current deployment, audience, live endpoint or authorization.

Do not regenerate a historical catalog from current names/parents or reinterpret old rows to fit a new schema. Make an explicit versioned migration, retain backward compatibility where promised, and test old and new consumers. Content import gates and scientific evidence requirements are in [HISTORY.md](HISTORY.md); operational publication, access and recovery limits are in [OPERATIONS.md](OPERATIONS.md).
